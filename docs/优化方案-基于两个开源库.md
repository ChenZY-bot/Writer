# 基于两个开源库的优化方案

> 目标：AI 写手自动化流水线。三个必须解决的问题：**长剧情记忆 / 伏笔自圆其说 / 避免剧情复读**，
> 外加**热更新与人工监管**（纠偏、插入角色与剧情、合理安排走向）。

本文档只记录"为什么这么改"。改动本身在 `agent/canon`、`agent/quality`、`agent/memory`、
`agent/hitl`、`agent/nodes/gate_node.py`，测试在 `tests/`。

---

## 0. 结论先行

| 你的目标 | 原来的机制 | 改成了什么 | 开关 |
|---|---|---|---|
| 长剧情记忆 | 细纲做 query、Chroma top-8 单路召回 | 多路召回 + RRF 融合 + 去重 + MMR 多样性 | `fused_retrieval`（默认关） |
| 伏笔自圆其说 | 无（只靠模型自觉） | 伏笔账本：埋设章/承诺回收章/逾期，到期顶到写手面前 | `foreshadow_block`（默认开） |
| 避免剧情复读 | 审稿人 prompt 里一句话 | 三层机器判据：A 型死磕 / B 型短句轮换 / 章级 8-gram + 禁写桥段 | `quality_gate`（默认 dry） |
| 长剧情记忆（事实层） | 121 条永不收敛的事件文本 | 事件账本：去重 + 封顶 + 归档 + 可审计 | `events_ledger`（默认开） |
| 热更新 / 人工监管 | 一个写完就清空的 `director_notes.txt` | 带类型的指令收件箱，每章热读，落 canon，可审计 | `directives`（默认开） |

**为什么要这么多开关**：两个参考库都写着同一条纪律——"任何会改变排序/推送的开关默认关，
观察一轮再开"。小说流水线比它们更脆：一次错误拦截会打断一整本书的连载。

## 1. 从 dsh-degeneration-kit 拿到的四件东西

仓库：<https://github.com/walksls/dsh-degeneration-kit>

### 1.1 复读不是一种东西，是两种

它的 README 用 493 个真实会话日志统计出两型：

| | A 型 · 同一句死磕 | B 型 · 短句轮换 |
|---|---|---|
| 重复次数 | 10³–10⁴ | 20–200 |
| 样子 | `（读`×3369、`好`×10848 | `Let me write it.` → `Go.` → `Now.` → `OK.` |
| 可读性 | 像正常思考，信息量为 0 | 像正常推进，**最难认** |
| 单看"最高频单元占比 ≥20%" | 抓得到 | **抓不到**（每个短词只占 ~15%） |

`thinking-guard/lib/detect-v2.mjs` 给出的第二把尺子是：

```
shortShare   = 极短段（≤3 词）占比          >= 0.35
topUnitShare = 最高频 5 段合计占比          >= 0.50
样本段数                                    >= 25
```

实测分界：真样本 topUnitShare = 0.53/0.63/0.71，假阳性最高 0.41，阈值 0.50 落在空隙里。
而在役的单判据对英文为主的 8 个块**召回 0/8**。

**迁移到小说**：`agent/quality/repetition.py`
* 单元切分从"句号/换行"开始，长度单位改成"汉字 1 字 + 英文 1 词"（中文没有空格分词）；
* 短单元阈值取 8（对应原来的 ≤3 词）；
* 额外加一层**尾部 4000 字复检**——网文结尾最容易用排比短句灌水；
* 再加一层**章级 8-gram 重合**——`dsh` 管的是"单次生成内部"，小说还要管"这一章抄了上个月那一章"。

### 1.2 复读会自己喂自己

因为历史会被原样回传，一条复读留在上下文里，之后每一步都再发一遍。它的解法是"折叠（少产生）+
压缩（清库存）"。

**迁移到小说**：小说没有"思考块"可折叠，但有等价物——**把复读文本喂回给重写的写手**。
所以闸门的反馈里**只给判据和证据，不复述整段坏文本**；被拦下的稿子直接丢弃，不进 `context_memory`。

### 1.3 判据必须能失败

每个关键判据配一个"变异体"：改坏实现，判据必须红。`tests/` 里每条 hard 判据都有对应用例，
并且断言的是"会失败"，例如 `test_b_type_short_rotation_not_caught_by_a` 专门证明
"只用 A 型判据会漏掉 B 型"。

### 1.4 折叠说明要走 `user` 通道

它踩过的坑：宿主会静默丢弃不在名单里的 `developer` 消息。这条与小说无关，但它示范了
"**降级必须可观测**"——所以本项目的闸门会显式输出 `未执行的检查`（`skipped_checks`），
而不是在没花名册时假装白名单通过。

## 2. 从 fish 拿到的四件东西

仓库：<https://github.com/kinganyi/fish>

### 2.1 两段式召回 + 如实标记

先 AND 精确命中，无命中再 OR 回退，并把 `meta.fallback` 写出来。**不假装命中**。

**迁移**：`agent/tools/retriever_tools.py` 的融合模式里，每条候选带 `route` 字段，
最终结果按 `[历史来源: 第 N 章]` 标注；某一路检索失败只 warning，不拖垮整次检索。

### 2.2 排序四件套（`fish_push_rank.py`）

| 机制 | 参数 | 解决什么 |
|---|---|---|
| RRF | `k=60`，`Σ 1/(k+rank)` | 三把尺子（记忆分/字面命中/检索分）量纲不同，只比名次 |
| 三因子 | `recency^0.2 × importance^0.3 × relevance^0.5` | 路内重要性；importance = `log1p(n)/log1p(50)` |
| MMR | `λ=0.7`，相似度取 `max(同 kind+项目 0.4, 标题 Jaccard)` | 别让两条几乎一样的条目占两格 |
| 价值门 | `rel × (0.15 + 0.85·imp) ≥ floor` | 低于阈值不推 |

两个细节值得抄：

* **importance 不能是硬零**。fish 实测把 `value_floor=0.1` 打开后整条推送变空——
  因为新记忆 `access_count=0` → `importance=0` → 乘积 0 被一刀切。所以给了 0.15 的底。
* **MMR 的同项目相似度从 0.8 降到 0.4**。0.8 在 λ=0.7 时等价于给同项目候选加 0.343 的分数惩罚，
  会把正常候选系统性压掉。

**迁移**：`agent/memory/fusion.py` 原样实现 RRF（k=60）与 MMR（λ=0.7），但把
"importance"换成小说里有信号的量——片段被引用次数（没有则中性 1.0）；
相似度用正文 3-gram Jaccard（小说片段没有 kind/title）。

### 2.3 去重是"内容感知"的

读过的、过期的永久不再推；内容变了（`content_hash` 不同）才推新版。

**迁移**：Chroma 按 500 字切块、重叠 50 字，相邻块天然重复 10%；同一事件被写过多次更是常态。
`fusion.dedupe()` 对"**包含关系**"（一块是另一块的子串）也判重——这是 3-gram Jaccard 的盲区
（实测 0.788 < 0.80 阈值，漏判）。包含关系时保留信息更全的那条。

### 2.4 默认关 + 判据钉住

四个排序开关默认全关，行为由 `test_rrf_fuse / test_factors / test_mmr_value` 逐条钉住。

**迁移**：本文档第 5 节的开关表；每个开关都有对应的单测或 dry 模式。

## 3. 当前系统的三个结构性缺陷（改造依据）

### 3.1 主关卡在结构上失效

`memory/state.json` 里 `global_events` 有 **122 条，其中"进行中" 121 条，"已完结" 1 条**。
而 `prompt/reviewer_prompt.txt` 的判据是"只有重演【已完结】的历史大事件才打回"。
**"进行中"永不收敛 → 这条判据永不触发。** 全量日志：207 次审查，打回 10 次（4.8%）。

### 3.2 记忆是单路相似度，不是"该用什么"

`chapter_plan` 是"计划文本"，正文片段是"已写文本"，两者相似度天然偏低。捞回来的常常是
同题材的其他章节。而且没有时效、没有多样性、没有去重。

### 3.3 人工入口只有一条单向管道

`config/director_notes.txt`：自由文本 → 拼到 outline 末尾 → 写完一章就 `clear_director_notes()`。
结果：**插入的角色下一章就忘**（没进 canon），**改过的设定不可审计**，**没法回滚重写**。

## 4. 新架构

```
                    ┌──────────────── 每章热读 ────────────────┐
                    │ config/directives/inbox.jsonl            │
                    │   insert_character / lock_fact /         │
                    │   steer_plot / ban_motif / rewrite_chapter│
                    └───────────────┬──────────────────────────┘
                                    ▼
config/outline.txt ──┐      ┌────────────────┐
memory/glossary.json ┼─────▶│ main: 拼注入块  │──▶ director_notes
memory/foreshadow.json┤      │ (canon/伏笔/禁写)│      （planner & writer 已消费此字段）
banned_motifs.json ──┘      └────────────────┘
                                    │
   ┌─────────┐   ┌────────┐   ┌─────────┐   ┌──────────┐   ┌────────┐
   │ Planner │──▶│ Writer │──▶│  Gate   │──▶│ Reviewer │──▶│ Memory │
   └─────────┘   └────────┘   └────┬────┘   └──────────┘   └───┬────┘
        ▲                           │ failed                    │
        │                           ▼                           ▼
        │                      back to Writer          EventLedger(去重/封顶)
        └───────────────────────────────────────────   Chroma(切块入库)
                                                     context_memory(5 章窗口)
```

* **Gate** 是新增节点：只做机器能判的事（字数/格式/锚点/白名单/禁写/复读），
  过了才进 Reviewer。这样 LLM 审稿只评"文笔、人物、OOC"这类主观项。
* **Memory** 的事件表改由 `EventLedger` 接管，`state.json` 同时存 `events_json`（结构化）和
  `global_events`（渲染文本，兼容旧代码与回滚）。
* **注入点只有一个**：`director_notes`。这是因为 planner 和 writer 都已经消费它，
  不需要改任何 prompt 模板——**改动面越小，回归风险越小**。

## 5.5 校准：拿已有的 88 章当回归集

新判据不能只在合成样本上通过。把本机一部**已写到 88 章的私有作品**全部过一遍闸门
（`output/<作品目录>/`，这份语料不入库）
（`target_words=2500`、带上一章锚点、查最近两章），得到第一版真实数据：

| 判据 | 第一版命中 | 处理 | 校准后 |
|---|---|---|---|
| `G-TITLE` warn | 88 | 文件头本来就有"第 N 章"，是测试口径问题，不是判据问题 | 88（对 draft 不触发） |
| `G-ANCHOR` warn | **82** | 无条件比对末十字：正常衔接根本不会重复上一章的最后 10 个字 | **0** |
| `G-WORDS` hard | **23** | 统计口径是"汉字+英文词"，不含标点；下限 0.80 太紧 | **6** |
| `G-REPEAT-A` hard | **20** | **真 bug**：中文对白按句号切会留下单独的 `”`，它一度占满 20% | **0** |

三个都是"判据必须能失败"这条纪律抓出来的：

1. **`”` 被当成句子**。第 3/5/8 章里 `”` 分别出现 16/18/15 次，占句数 20%+，
   A 型判据于是一口咬定这三章在死磕。修法：`split_units` 丢掉"零信息量单元"。
   回归用例：`test_quote_only_units_do_not_count`。
2. **锚点判据 93% 误报**。改成两个更锐的判据：
   * 只有当上一章结尾**没有终止标点**（话没说完）时才要求字面接上；
   * 无论锚点如何，开篇出现"第二天/次日/与此同时/一周后"等词就提示 `G-TRANSITION`。
3. **字数下限**。`count_words` 不计标点，2500 字的稿子实际约 2200–2300。
   下限从 0.80 调到 0.72（1800 字），命中从 23 章降到 6 章。

**这 6 章不是误报**：第 16/26/64/65/74/75 章确实短（最短 1530 字），
换到 `enforce` 会被要求补写——这正是它该做的事。

## 6. 落地顺序与验收判据

### 第 1 步（已完成，可直接跑）

```powershell
python -m unittest discover -s tests -t .   # 90 passed
```

### 第 2 步：先 dry 观察一轮

保持 `quality_gate: "dry"`，跑 3~5 章，看 `logs/Gate_*.log`：

* 若 `G-WORDS` 频繁报警 → 说明 2500 字目标与模型产出不稳，考虑把 `target_word_count` 调成区间；
* 若 `G-REPEAT-B` 误报 → 把 `b_short_share_min` 抬高或 `short_weight_max` 调小；
* 若 `G-ANCHOR` 频繁但人工看起来衔接正常 → 说明字面锚点太严，应该降级为纯提示（它现在本来就是 warn）。

### 第 3 步：开启 enforce

```yaml
quality_gate: "enforce"
```

判据：连续 10 章，闸门打回率 < 20%，且被打回的章节能按反馈改好（看 `revision_count`）。

### 第 4 步：开启融合检索

```yaml
fused_retrieval: true
retrieval_factors: false   # 先只开融合，再开加权
```

对比 `logs/System_*.log` 里"融合检索：N 路 → M 条候选 → K 条"，确认 K 稳定在 6~8。
观察 3 章再开 `retrieval_factors`。

### 第 5 步：接入人工干预

现在就可以用（`directives: true` 默认开）：

```powershell
# 插入一个角色，永久生效
python -m agent.hitl.directives add insert_character --id D-001 `
  --payload '{"name":"示例角色","setting":"旧山神社巫女，三年前救过主角"}'

# 禁止再写学园祭
python -m agent.hitl.directives add ban_motif --id D-002 --payload '{"motif":"学园祭"}'

# 第 88 章 OOC，回滚重写
python -m agent.hitl.directives add rewrite_chapter --id D-003 `
  --payload '{"chapter":88,"confirm":true}' --note "第88章人物 OOC"

# 看待生效
python -m agent.hitl.directives list
```

### 第 6 步：维护伏笔账本

```powershell
python -m agent.canon.foreshadow add "木剑的裂痕" --planted 12 --due 20 --owner 叶凡
python -m agent.canon.foreshadow due --chapter 21     # 看该收哪些坑
python -m agent.canon.foreshadow pay "木剑的裂痕" --chapter 21 --payoff "以裂痕为引，木剑认主"
```

长期看，第 3 步之后可以给 Memory 加一个"从本章提取伏笔"的 LLM 调用，
让账本自动增长；**但第一版故意做成手动**，因为自动提取的假阳性会污染账本，
而账本一旦被污染，比没有账本更糟。

## 7. 已知限制（不粉饰）

1. **首次启用事件账本会归档 100+ 条旧事件**。已备份 `memory/state.json.bak-before-ledger`；
   回滚方式：`events_ledger: false` 并还原备份。
2. **回滚重写不回滚向量库**。第 88 章作废后，它的片段仍在 Chroma 里，`retrieve` 仍可能捞到。
   彻底一致需要重建 collection（按章删除 + 重新入库），当前未实现。
3. **章级 8-gram 只查最近 2 章**。更早的"桥段复读"靠禁写桥段名单兜底，不是自动发现。
4. **人物白名单默认跳过**（没有花名册）。`G-WHITELIST` 会显式写进 `skipped`，不会假装通过。
5. **A/B 阈值是从"模型思考文本"迁到"中文小说正文"的**，方向对，但分界值需要你用真实章节校准一轮。
6. **没有跑过端到端**。本机 `python` 是坏的（0 字节 stub）、`agent_config.yml` 里没有 API Key，
   所以只能验证到"纯逻辑单测 90 通过 + 全部文件编译通过"。第一次真跑请先用 `dry`。
7. `AgentState` 统一后，`writer_node` 等文件里的局部 `AgentState` 已删除；
   若外部脚本曾 `from agent.nodes.writer_node import AgentState`，请改从 `agent.state` 导入。
